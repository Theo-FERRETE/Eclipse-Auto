# Front : le site en deux langues

Le **site public** est disponible en français et en anglais. Le **back-office admin reste
en français** : c'est un outil interne, son public ne change pas avec la langue du
visiteur. C'est un choix assumé, pas un oubli.

| Fichier | Rôle |
|---|---|
| `lib/i18n.js` | La configuration i18next : langues, détection, mémorisation |
| `locales/fr.json`, `locales/en.json` | Les textes, une clé par chaîne affichée |
| `components/LanguageSwitcher/` | La bascule FR / EN, placée dans la navbar |
| `lib/apiError.js` | Traduit les erreurs renvoyées par l'API |

## Pourquoi i18next

Trois dépendances (`i18next`, `react-i18next`, `i18next-browser-languagedetector`), environ
22 Ko gzip dans le bundle, isolées dans leur propre chunk (`manualChunks` de
`vite.config.js`). En échange, on ne réécrit pas soi-même la détection de langue, la
mémorisation du choix, l'interpolation de variables et la gestion du balisage dans une
phrase traduite.

## Comment un texte est traduit

Dans un composant :

```jsx
import { useTranslation } from 'react-i18next'

const { t } = useTranslation()
return <h1>{t('catalogue.title')}</h1>
```

La clé `catalogue.title` est cherchée dans `locales/fr.json` ou `locales/en.json` selon la
langue courante. **Aucun texte affiché n'est écrit en dur dans un composant public.**

### Quand la phrase contient du balisage

Un `t()` renvoie une chaîne : il ne peut pas produire un `<strong>` au milieu d'une phrase.
Et on ne veut pas découper la phrase en JSX, parce que l'ordre des mots change d'une langue
à l'autre. D'où le composant `<Trans>` :

```jsx
<Trans
  i18nKey="reservation.successDesc"
  values={{ vehicle: 'Ferrari 488' }}
  components={{ b: <strong /> }}
/>
```

```json
"successDesc": "Votre demande pour la <b>{{vehicle}}</b> a bien été enregistrée."
```

Le traducteur déplace librement le `<b>` et le `{{vehicle}}` dans sa phrase.

## La langue est choisie une fois, puis mémorisée

`lib/i18n.js` configure la détection dans cet ordre :

1. **`localStorage`** (clé `eclipse-lang`) : le choix explicite de l'utilisateur ;
2. **`navigator`** : à défaut, la langue du navigateur.

Un visiteur dont le navigateur est en anglais arrive donc directement sur la version
anglaise, et son clic sur « FR » est retenu pour ses prochaines visites. `load:
'languageOnly'` fait retomber `en-US` ou `fr-FR` sur `en` et `fr` ; sans lui, ces valeurs ne
correspondraient à aucune langue connue et repartiraient sur le fallback français.

À chaque changement, `syncDocument()` met à jour deux choses que React ne gère pas, puisqu'il
ne rend que `#root` :

- l'attribut `lang` du `<html>`, utilisé par les lecteurs d'écran et la césure ;
- la `<meta name="description">`, lue par les moteurs de recherche.

## Ne jamais stocker du texte traduit dans un state

C'est le piège principal. Un message d'erreur rangé dans un `useState` sous forme de texte
reste figé dans la langue qu'il avait au moment de l'erreur, même après un changement de
langue. Les composants stockent donc **une clé** ou **un booléen**, et traduisent au rendu :

```jsx
// Non : le texte est figé
setError('Email ou mot de passe incorrect.')

// Oui : la clé est traduite à chaque rendu
setError('auth.loginFailed')
// ...
{error && <div className="form-error">{t(error)}</div>}
```

## Les données venues de la base

Trois cas, traités différemment.

| Donnée | Traitement |
|---|---|
| Carburant, transmission, mode de paiement, statuts | **Traduits.** Ce sont des valeurs fermées, connues à l'avance |
| Marque, modèle, nom d'un équipement | **Affichés tels quels.** « Ferrari » ne se traduit pas |
| Description d'un véhicule | **Affichée telle quelle**, dans la langue où l'admin l'a saisie |

Pour le premier cas, `lib/utils.js` expose `translateFuel()`, `translateTransmission()` et
`translatePaymentMethod()`. Point important : **seul l'affichage est traduit, jamais la
valeur**. Le catalogue filtre sur `fuel_type === 'Essence'`, la valeur de la base ; c'est
le libellé du bouton qui devient « Petrol ».

Une valeur absente du dictionnaire (un carburant ajouté en base sans traduction) est
affichée telle quelle plutôt que de disparaître.

### Prix et dates

`formatPrice()`, `formatNumber()`, `formatDate()` et `formatDateTime()` lisent la langue
courante dans le singleton i18next et formatent en `fr-FR` ou `en-GB` :

| | Français | Anglais |
|---|---|---|
| Prix | `€ 25 000` | `€ 25,000` |
| Date | `25/09/2026` | `25/09/2026` |

`en-GB` plutôt que `en-US` : le jour reste avant le mois, comme partout ailleurs sur le
site. Un `25/09` qui deviendrait `09/25` d'une langue à l'autre serait une source d'erreur
pour un client qui réserve un essai.

## Les erreurs de l'API

L'API est écrite en français. Un client bilingue ne peut pas afficher ses phrases telles
quelles. Les routes publiques renvoient donc **un code en plus du message** :

```json
{ "error": "Ce véhicule n'est plus disponible.", "code": "VEHICLE_UNAVAILABLE" }
```

Le serveur les produit avec `lib/apiError.js` (`fail(res, 409, 'VEHICLE_UNAVAILABLE', '…')`),
le client les traduit avec le sien :

```jsx
if (!res.ok) throw new Error(await readApiError(res))
```

`readApiError` cherche `apiErrors.VEHICLE_UNAVAILABLE` dans les traductions. S'il ne trouve
pas le code — erreur inattendue remontée par Supabase, route pas encore migrée — il retombe
sur le message français du serveur, puis sur un texte générique. **Aucune erreur ne peut
donc s'afficher vide.**

Pourquoi un code plutôt qu'une table de correspondance sur les phrases françaises : le jour
où tu reformules un message côté serveur, une correspondance par phrase casserait en
silence, sans erreur au build ni au lint. Un code est un contrat explicite entre l'API et
ses clients — c'est aussi ce qui permettrait à une application mobile de s'y brancher.

## Ce que les tests garantissent

| Test | Ce qu'il empêche |
|---|---|
| `__tests__/lib/locales.test.js` | Une clé ajoutée dans une langue et oubliée dans l'autre ; une valeur vide ; un `{{variable}}` perdu à la traduction |
| `__tests__/lib/utils-i18n.test.js` | Un prix ou un carburant qui ne suivrait pas la langue |
| `__tests__/components/LanguageSwitcher.test.jsx` | Une bascule de langue qui ne changerait pas l'affichage |

Les autres tests vérifient des textes français : `__tests__/setup.js` fige donc la langue
en français avant de charger i18next. Sans ça, jsdom annonce `en-US` et les assertions
casseraient pour une raison sans rapport avec ce qu'elles vérifient.

## Ajouter un texte

1. Ajouter la clé dans `locales/fr.json` **et** `locales/en.json` ;
2. L'utiliser via `t('ma.cle')` dans le composant ;
3. `npm test` — le test de cohérence refuse une clé présente d'un seul côté.

## Limites connues

- Les **emails de confirmation et les factures PDF** sont générés en français, quelle que
  soit la langue choisie sur le site. Les rendre bilingues suppose de stocker la langue du
  client en base et de la faire descendre jusqu'aux templates du serveur.
- Les **descriptions de véhicules** saisies par l'admin ne sont pas traduites.
- L'URL ne porte pas la langue (pas de `/en/catalogue`). Conséquence : les moteurs de
  recherche n'indexent que la version française. Une vraie stratégie SEO multilingue
  demanderait des URL distinctes et des balises `hreflang`.
