Les 6 questions, celles qui tombent

1Où et quand le token est-il créé ?

Chez Supabase, jamais chez moi. Au moment où Supabase a vérifié le mot de passe, donc à la connexion, et aussi à l'inscription. Il le signe avec une clé que lui seul détient, et il est valable 1 heure.

client/src/lib/auth.jsmon code
// Le mot de passe part direct chez Supabase, l'app ne le voit jamais.
export async function login(email, password) {
  const { data, error } = await supabase.auth.signInWithPassword({ email, password })
  if (error) throw error
  return data
}

La phrase qui compte. « Mon serveur n'est pas dans la boucle. » Il ne voit le token qu'à la requête suivante. Aucune ligne de mon code ne participe à sa création.

Si on pousse. Il est aussi recréé automatiquement vers 55 min, à partir du refresh_token, sans que l'utilisateur retape quoi que ce soit.

2Comment et où est-il stocké ?

Dans le localStorage du navigateur. C'est la librairie supabase-js qui l'y écrit, ce n'est pas mon code. Et côté serveur, nulle part : aucune table de sessions. Le token arrive, sert, et il est oublié.

Il y a en fait deux jetons. L'access_token, valable 1 h, est celui que j'envoie à mon API. Le refresh_token reste dans le navigateur, n'est jamais envoyé à mon serveur, et sert uniquement à obtenir un nouvel access_token.

client, à chaque appel protégémon code
// getSession() est rappelé juste avant chaque fetch, jamais gardé dans un useState :
// un token mis en mémoire serait périmé au bout d'une heure.
const { data: { session } } = await supabase.auth.getSession()
const res = await fetch(`/api/reservations/${id}/cancel`, {
  method: 'PATCH',
  headers: { 'Authorization': `Bearer ${session?.access_token}` },
})

Le détail qui fait sérieux. Expliquer pourquoi getSession() est rappelé à chaque fois plutôt que stocké dans un état React : parce qu'un token gardé en mémoire serait périmé au bout d'une heure.

Slide 17, à placer soi-même, une fois

Un point d'honnêteté : mon dossier écrit que le token vit en mémoire. En relisant mon code pour cet oral, j'ai vérifié, il est dans le localStorage, c'est le défaut de la librairie Supabase. Ça ne change rien à mon raisonnement CSRF, qui tient au fait qu'il n'est pas dans un cookie. Ça change l'exposition au XSS, d'où le cookie httpOnly en tête de mes améliorations.

3Comment est-il vérifié ?

Mon middleware extrait le token de l'en-tête Authorization: Bearer, puis appelle supabase.auth.getUser(). C'est Supabase qui valide la signature et l'expiration. Je n'ai pas la clé, donc je délègue la vérification. Si ça échoue : 401. Et ce n'est qu'après cette réponse que je fais confiance à req.user.

server/middleware/auth.jsmon code
// Extrait le token de « Authorization: Bearer <token> ».
function getTokenFromHeader(req) {
  const header = req.headers.authorization
  if (!header || !header.startsWith('Bearer ')) return null
  return header.split(' ')[1]
}

// C'est Supabase qui vérifie la signature et l'expiration.
async function verifyToken(token) {
  const { data: { user }, error } = await supabase.auth.getUser(token)
  if (error || !user) return { error: 'Token invalide ou expiré.' }
  return { user }
}

async function requireAuth(req, res, next) {
  const { user, error } = await verifyToken(getTokenFromHeader(req))
  if (error) return res.status(401).json({ error })
  req.user = user
  next()
}

Ne surtout pas dire « je vérifie la signature avec la clé publique ». Ce serait faux : je délègue à Supabase.

Si on pousse (« ça fait un appel réseau à chaque requête ? »). « Oui. La contrepartie, c'est que je ne fais pas aveuglément confiance à un token non expiré. Vérifier la signature en local serait plus rapide, c'est une optimisation identifiée. »

4Où est-il vérifié ?

Côté serveur, dans un middleware placé entre la route et le contrôleur. Il est déclaré dans la définition même de la route : si la vérification échoue, le contrôleur n'est jamais atteint.

server/routes/reservations.jsmon code
router.get('/',             requireAuth,  reservationController.listMine)
router.post('/',            requireAuth,  reservationController.create)
router.patch('/:id/cancel', requireAuth,  reservationController.cancel)

router.get('/all',          requireAdmin, reservationController.listAll)
router.patch('/:id/status', requireAdmin, reservationController.updateStatus)

Le point fort. « La protection n'est pas dans le contrôleur, elle est sur la route. » On lit la sécurité d'une route sur une seule ligne, sans ouvrir le contrôleur.

Et les routes sans middleware ? « Le catalogue est public, c'est volontaire : router.get('/', vehicleController.list). Un visiteur doit pouvoir voir les véhicules sans compte. »

Les deux moitiés de la réponse

1. Jamais côté front. Le front cache les boutons, il ne protège rien : on peut appeler l'API directement avec Postman.

2. Et une deuxième couche dans la base : la RLS. Même en contournant entièrement mon serveur, la base refuserait.

5Comment est gérée la déconnexion ?

J'appelle supabase.auth.signOut(). Ça efface la session du localStorage et ça coupe le renouvellement automatique : sans refresh_token, plus aucun nouveau token ne sera émis.

Mon serveur, lui, n'a rien à faire. Il n'a rien à effacer, puisqu'il ne stocke aucune session. C'est la conséquence directe du sans-état.

client/src/lib/auth.jsmon code
export async function logout() {
  const { error } = await supabase.auth.signOut()
  if (error) throw error
}

L'aveu à assumer, il va venir. « Un access_token déjà émis reste valable jusqu'à son expiration, 1 h au maximum. Je ne peux pas le révoquer : c'est la contrepartie assumée du sans-état. Ce que la déconnexion coupe, c'est le renouvellement. »

Ne pas s'aventurer plus loin

Ne pas prétendre que la révocation est immédiate côté serveur, ce n'est pas testé. La réponse ci-dessus est exacte et suffit. Si on insiste : « pour une révocation immédiate, il faudrait une liste de tokens révoqués côté serveur, et je perdrais le sans-état. C'est l'arbitrage. »

6Comment est géré le hash du mot de passe ?

Pas par moi, et c'est le point. Il n'y a aucun mot de passe et aucun hash dans ma base : ils sont dans auth.users, le schéma géré par Supabase. Supabase les hashe avec bcrypt.

Un hash, ce n'est pas un chiffrement : on ne peut pas revenir en arrière. À la connexion, Supabase hashe le mot de passe reçu et compare les deux empreintes, il ne déchiffre jamais rien. Et bcrypt est lent et salé par conception : le sel empêche les tables pré-calculées, la lenteur rend le test de millions de mots de passe trop coûteux.

La chute. « Refaire ça soi-même, c'est le refaire mal. »

Et la preuve, en 4 lignes. Ma fonction login() passe password directement à Supabase. Il ne traverse jamais mon code : aucun mot de passe dans ma base, aucun dans mes logs. Pas parce que je fais attention, parce qu'il n'y en a jamais eu.

Le repère

Mon serveur et le mot de passe ne sont jamais dans la même colonne. Si les deux apparaissent dans la même phrase, il y a un mélange.

Les 4 mots

JWT Une preuve signée. Lisible par tous, infalsifiable par tous. Signé n'est pas chiffré. Un caractère modifié et la signature est morte. Donc jamais rien de confidentiel dedans.
Trigger Une consigne posée sur une table : « chaque fois qu'il se passe X ici, fais Y ». C'est la base qui l'exécute, seule. Se déclenche quoi qu'il arrive, peu importe par où la donnée entre.
RLS Des règles dans la base qui décident, ligne par ligne, qui lit ou écrit quoi. Ma deuxième couche : même en contournant mon serveur, la base refuserait.
Stateless Mon serveur ne garde aucune trace d'une requête à l'autre. Il en reçoit des centaines, c'est la mémoire qu'il ne garde pas. D'où le token à chaque fois.

REST et le sans-état, c'est la même chose

Mes slides disent « API REST », ma fiche dit « stateless ». Ce n'est pas une contradiction : le sans-état est l'une des contraintes fondatrices de REST.

Ne pas fusionner ces deux questions

Pourquoi le navigateur parle directement à Supabase ? Pour que le mot de passe ne traverse jamais mon code. Séparation des métiers.

Pourquoi chaque requête porte un token ? Parce que mon API est stateless. Contrainte REST.

Le test : je pourrais faire passer la connexion par Express, mon API resterait parfaitement stateless. Ce serait juste une mauvaise idée. Donc le sans-état n'oblige pas le navigateur à parler à Supabase.

Ce ne sont pas deux bases de données, ce sont deux tiroirs du même meuble. La preuve : profiles.id pointe vers auth.users.id, et une clé étrangère ne peut pas relier deux bases séparées. C'est aussi ce qui rend le trigger possible : un trigger ne traverse jamais deux bases.

Si on pousse plus loin

+Je peux lire le contenu du token !

Oui, c'est signé, pas chiffré, et c'est volontaire. La signature ne sert pas à cacher, elle sert à garantir que personne n'a triché avec le contenu. Je n'y mets donc rien de confidentiel : un identifiant et un rôle.

L'image : une carte d'identité. Tout le monde peut la lire. Personne ne peut en fabriquer une.

+Je remplace role: client par role: admin

La signature ne colle plus, Supabase rejette le token, c'est 401. Et en amont, le rôle est dans app_metadata, que l'utilisateur ne peut pas modifier lui-même, contrairement à user_metadata où je ne mets que le prénom et le nom.

server/middleware/auth.jsmon code
  // 401 = je ne sais pas qui tu es.
  if (error) return res.status(401).json({ error })

  // 403 = je le sais, mais tu n'as pas le droit.
  if (user.app_metadata?.role !== 'admin') {
    return res.status(403).json({ error: 'Accès réservé aux administrateurs.' })
  }

Les deux codes sont à trois lignes d'écart dans la même fonction. Pour expliquer 401 contre 403, montrer ça.

+J'annule la réservation d'un autre client ?

Non. Le client_id vient toujours du token, jamais du corps de la requête. Le client ne choisit jamais au nom de qui il agit.

server/controllers/reservationController.jscréation et annulation
// A la création : client_id vient du token, jamais de req.body.
await reservationModel.create({ vehicle_id, client_id: req.user.id, status: 'pending' })

// A l'annulation : sans ce test, n'importe qui pourrait annuler
// la réservation d'un autre. Etre connecté ne suffit pas.
if (reservation.client_id !== req.user.id) return res.status(403).json({ error: 'Accès refusé.' })

Deux protections différentes : à la création il ne peut pas choisir son identité, à l'annulation on vérifie qu'elle lui appartient. Le nom à la fin : « c'est la faille qu'on appelle IDOR, elle est couverte par un test. »

+Si on vole le token ?

Il agit comme la victime, pendant 1 h maximum. Mais il ne peut ni en déduire le mot de passe, ni en fabriquer un autre. Et il n'a que l'access_token, le refresh_token n'est jamais envoyé à mon API.

Reprendre la main : « d'où le cookie httpOnly en tête de mes améliorations. »

+Votre clé Supabase est publique !

Oui, par conception. Elle ne dit pas « tu es admin », elle dit « tu es un client légitime de ce projet ». C'est une adresse, pas une autorisation. Et même en appelant Supabase directement avec, la base refuserait : les règles sont dans la base, ligne par ligne.

Le nom à la fin : « ça s'appelle la RLS, c'est ma deuxième couche. »

+Qui crée le profil à l'inscription ?

Mon serveur n'est pas là à l'inscription, aucune ligne de mon code ne peut le créer. La base le fait seule : on_auth_user_created appelle handle_new_user, dans la même transaction.

Le trajet : j'envoie le prénom dans user_metadata à l'inscription, Supabase crée le compte, puis le trigger le recopie dans profiles.

Sur SECURITY DEFINER : « l'utilisateur vient d'être créé, il n'est pas encore pleinement authentifié, il n'aurait pas le droit d'écrire dans profiles. La fonction s'exécute avec les droits du propriétaire. »

+C'est quoi, une API REST ?

Une architecture, pas seulement des verbes HTTP.

  • Client-serveur : le front et l'API sont séparés
  • Sans état : chaque requête est autonome, elle porte tout ce qu'il faut
  • Des ressources identifiées par des URL : /vehicles, /reservations
  • Des verbes qui disent l'intention : GET, POST, PUT, DELETE
  • Des codes qui disent le résultat : 200, 401, 403, 404

Ne pas réciter les cinq. Les deux premiers suffisent, et le deuxième explique toute mon authentification.

Mes 3 pièges

  1. Ne jamais dire « le serveur ». Il y en a deux. Dire Supabase ou mon serveur. Et pas « mon serveur Supabase », ça recolle les deux.
  2. Toujours ajouter la phrase d'après. Mes conclusions sont bonnes, c'est le donc qui manque. « Il voit la preuve » appelle « et jamais le mot de passe ». C'est la deuxième moitié qui prouve que j'ai compris.
  3. Le problème d'abord, le mot technique après. Expliquer le mécanisme, puis lâcher le nom : IDOR, RLS, stateless. Le nom seul ressemble à une récitation.
Et surtout

Ne jamais dire « je sais pas » sec. Dire « je réfléchis à voix haute » et partir de ce que je sais. Un jury note le raisonnement, pas la récitation. Une réponse partielle construite à voix haute vaut dix fois un blanc.
